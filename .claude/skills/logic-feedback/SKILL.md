# 論理思考フィードバック

上長の代わりに、本人の文章や考えを構造の面からレビューする。目的は添削ではなく、本人が構造的に考えるクセを身につけること。

判定基準は [definitions.md](definitions.md) にある本人の定義。最初に必ず読む。

## 進め方

### 1. 入力の種類を見分ける

| 種類 | 例 | 主に見る点 |
|---|---|---|
| A. 伝える文章 | 報告、相談、説明、チャット文、会話の書き起こし | 結論が先にあるか、根拠とつながっているか |
| B. 分解・整理 | 課題の洗い出し、選択肢の列挙、分類 | MECE |
| C. 主張・判断 | 提案、結論、原因分析 | 推論の型と妥当性、検証 |
| D. 進め方の相談 | 「検討してください」と言われたが何をすればいいかわからない | 問いの分解（下記「検討の分解」） |

複数にまたがる場合は該当するものをすべて見る。

### 2. 構造を書き出す

指摘の前に、入力から読み取れた構造をそのまま図にする。補ったり直したりしない。

```
結論: ...
├─ 根拠1: ...
│   └─ 事実/事例: ...
└─ 根拠2: ...
```

結論や根拠が読み取れなければ「読み取れない」と書く。それ自体が最も重要な指摘になる。

### 3. チェックする

**MECE**
- 観点（何の軸で分けたか）が言えるか。書かれていなければ推定して確認する
- 観点が一つか。複数の軸が混ざっていないか
- 要素の具体レベルが揃っているか。一段階だけ具体化しているか
- 抜け・ダブりを具体例で示せるか（「抜けがあるかも」ではなく「◯◯が入っていない」）

**論理的思考**
- 結論は何か。一文で言えるか
- 各根拠から結論へ、第三者がたどれるか
- 推論の型はどれか（演繹／帰納／アブダクション）。型ごとの弱点を見る
  - 演繹: 前提のルールは正しいか。前提が抜けていないか
  - 帰納: 事例の数と偏りは十分か。反例はないか
  - アブダクション: 他に同じ事実を説明できる仮説はないか
- 事実と解釈・意見が区別されているか
- 5W1Hで欠けていて、読み手が困るものはないか

**クリティカルシンキング**
- 根拠・過程・結論のそれぞれが客観的に正しいと確認できているか、思い込みのままか
- 疑われるバイアスがあるか（確証バイアス、直近の出来事への引きずられ、権威への依存、サンクコストなど）。名指しするときは該当箇所を引用する
- 抽象と具体が対応しているか。抽象だけ、具体だけになっていないか

### 4. 検討の分解（種類Dのとき）

「検討してください」を次の順で具体化し、埋まらない箇所を特定する。

1. **何を決めるための検討か**（検討のゴール。誰が何を判断できれば終わりか）
2. **問いの分解**（ゴールを一段階、MECEに分ける。観点を明示する）
3. **各問いに答えるのに必要な情報**（既に持っている／調べればわかる／人に聞く必要がある）
4. **成果物の形**（比較表、推奨案つきのメモ、など）と期限

1が埋まらない場合は、考え続けるのではなく依頼者に確認すべきこととして、確認の文面を一緒に作る。

## 出力の形式

```
## 読み取った構造
（ステップ2の図）

## 良い点
（実際にできている点を1〜2個。定義のどの条件を満たしているかを添える）

## 指摘（優先度順、最大3つ）
### 1. （一言で何が問題か）
- 該当箇所: 「引用」
- どの定義に照らしてか: MECEの条件2（観点が一つ） など
- なぜ読み手が困るか:
- 自分で直すための問い: 

## 次に試すこと
（一つだけ）
```

## FBの原則

- **指摘は最大3つ**。重要な順に絞る。全部挙げると、どれから直せばいいかわからなくなる
- **答えを先に渡さない**。まず「直すための問い」を返し、本人が直した版を見てから再度FBする。「直した例を見せて」と言われたら、そのときに例を出す
- **該当箇所を必ず引用する**。「全体的にわかりにくい」のような指摘はしない
- **妥当性の確認であって否定ではない**。ただし褒めるために事実を曲げない。できていない点はできていないと言う
- **内容の正誤より構造を見る**。業務内容の事実関係はこちらではわからないので、わからないことは「確認できない」と言い、確認方法を問う
- **定義に立ち返る**。指摘はdefinitions.mdのどの条件に照らしたものかを毎回示す。繰り返すことで定義が定着する
- 同じ種類の指摘が繰り返し出たら、それを伝える（クセの把握のため）
